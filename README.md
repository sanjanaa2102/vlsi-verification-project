# VLSI / Digital Design Verification Portfolio Project

A cocotb-based digital design verification project built around two
genuinely different DUTs -- a UART transmitter and an APB4-Lite register
block -- each with its own full verification environment (driver,
monitor, reference model, scoreboard, protocol checker, functional
coverage, constrained-random stimulus), a shared DUT-agnostic mutation-
testing engine, a unified reproducible regression runner with CI, and a
small formal-verification layer on the APB DUT. It also includes a
separate research track (`phase2_llm/`) comparing a hand-written UART
testbench against one generated by an LLM, scored by the same mutation
suite.

**What this is not:** this project does not claim to be "fully
verified" or "100% verified." Every verification mechanism here has a
specific, bounded scope -- what each one actually proves, and does not
prove, is documented explicitly in `VERIFICATION_STRATEGY.md`. Treat any
single metric (a coverage percentage, a mutation score, a formal PASS)
as one data point among several, not a project-wide grade.

## Prerequisites

- Linux (developed and tested on WSL2/Ubuntu; no Linux-specific
  assumptions beyond standard packages)
- Python 3.12
- [Icarus Verilog](http://iverilog.icarus.com/) (`iverilog`, `vvp`) --
  install via your system package manager, e.g. `apt install iverilog`
- [GTKWave](https://gtkwave.sourceforge.net/) (optional, for viewing
  waveforms) -- `apt install gtkwave`
- `git` (for fetching SymbiYosys automatically on first formal-verification run)

Everything else (cocotb, cocotb-coverage, Verible, the formal-verification
toolchain) is pip-installable -- no other system packages, no commercial
EDA tools, no paid services or licenses anywhere in this project.

## Installation

```bash
git clone <this-repo-url>
cd vlsi-verification-project

python3 -m venv venv
source venv/bin/activate

pip install -r requirements-lock.txt   # exact pinned versions (recommended)
# or: pip install -r requirements.txt  # direct dependencies, latest compatible transitive versions
```

`requirements-lock.txt` is what CI actually installs from, and is
deliberately narrower than `requirements.txt` -- see that file's header
for exactly what it covers and why (it excludes `phase2_llm`-only and
currently-unused dependencies, reviewed by hand, not a blind `pip freeze`).

Verify the toolchain:

```bash
iverilog -V
python -c "import cocotb; print(cocotb.__version__)"
verible-verilog-lint --version
```

## Quick start: the complete regression, one command

```bash
python run_regression.py
```

This runs, in order: a toolchain sanity test, UART's directed/coverage-
directed/constrained-random/checker-only regressions, APB's directed/
constrained-random/checker-only/latency-only regressions, lint on both
RTL files, the full mutation suite for both DUTs, and all 3 formal
property proofs. It writes:

- `regression_results/report.json` -- machine-readable
- `regression_results/report.md` -- human-readable

Neither report collapses to a single number: test pass/fail, coverage
(per functional-coverage point), mutation score (per mechanism, per
defect category, per mutant), formal proof status (per property, with
proof type), and lint findings are each their own section, kept
deliberately separate (see `VERIFICATION_STRATEGY.md` for why).

Useful flags:

```bash
python run_regression.py --seed 12345      # pin both random suites (debugging/reproduction)
python run_regression.py --skip-mutation   # faster local iteration -- mutation testing is the slow part
python run_regression.py --skip-lint
python run_regression.py --skip-formal
```

**Reproducibility:** each random suite's seed is generated before that
suite runs (so it's recorded even on a hang or early failure), passed
through as `COCOTB_RANDOM_SEED=<seed>`, and printed/reported. This was
verified concretely, not assumed: running the same seed twice produces
byte-for-byte identical randomized stimulus (not just the same logged
seed number), and a different seed produces a genuinely different
sequence from the first transaction onward, for both DUTs. Reproduce a
specific run with `make MODULE=<suite> COCOTB_RANDOM_SEED=<seed>` inside
the relevant DUT directory.

**Failure diagnostics:** a failing suite's full simulator output is
saved to `regression_results/failures/<suite>/simulator_output.log`; for
single-`make` suites, that suite is automatically re-run with `WAVES=1`
(same seed, if applicable) to capture a waveform into the same
directory. A failing formal property similarly gets SymbiYosys's real
counterexample (`.vcd` + Verilog testbench replay + Yosys witness file)
copied there. Nothing extra is generated for suites that pass.

**Pass/fail semantics:** the overall regression fails if any test fails,
any suite errors or times out, mutation testing produces an `UNKNOWN`
verdict (a tool-level problem), or a formal property fails. A mutant
that legitimately `SURVIVED` a mechanism never designed to catch it
(e.g. a protocol checker against a pure data-value bug) does **not**
fail the build -- it's reported honestly in the mutation section, not
hidden and not treated as a regression.

## Individual DUT regressions

### UART (`phase1_uart/`)

```bash
cd phase1_uart
make clean && make                                  # directed regression (test_uart_tx.py)
make clean && make MODULE=test_uart_tx_coverage     # broadened directed sweep + coverage
make clean && make MODULE=test_uart_tx_random       # constrained-random regression
make clean && make MODULE=test_uart_tx_random COCOTB_RANDOM_SEED=<seed>   # reproduce a specific run
make clean && make MODULE=test_uart_tx_checker_only # protocol checker in isolation
```

### APB (`phase5_apb/`)

```bash
cd phase5_apb
make clean && make                                       # directed regression
make clean && make MODULE=test_apb_regblock_random       # constrained-random regression
make clean && make MODULE=test_apb_regblock_random COCOTB_RANDOM_SEED=<seed>
make clean && make MODULE=test_apb_regblock_checker_only # protocol checker in isolation
make clean && make MODULE=test_apb_regblock_latency_only # latency checker in isolation
```

Always run `make clean` before switching which `MODULE` you invoke in the
same DUT directory. `run_regression.py` and `mutation_suite.py` always do
this internally; a standalone `make MODULE=...` without it relies on
GNU Make's mtime-based rebuild check, which was observed (once, not
reliably reproduced -- see `LESSONS_LEARNED.md`) to reuse a stale
compiled binary from a previous invocation in the same directory.

## Coverage reports

Functional coverage is collected with
[cocotb-coverage](https://github.com/mciepluc/cocotb-coverage) and
exported as YAML after the relevant test module runs:

```bash
cd phase1_uart
make clean && make MODULE=test_uart_tx_coverage && cat sim_build/coverage.yml
make clean && make MODULE=test_uart_tx_random && cat sim_build/coverage_random.yml

cd ../phase5_apb
make clean && make MODULE=test_apb_regblock_random && cat sim_build/coverage_random.yml
```

`cocotb-coverage`'s `coverage_db` is a per-process singleton, so each
module's own report only reflects the CoverPoints *that module* samples
-- see `phase1_uart/VERIFICATION_PLAN.md` for why the "overall" number in
some of these reports is not the meaningful figure to read, and
`VERIFICATION_STRATEGY.md` for the actual measured percentages per
CoverPoint.

## Mutation testing reports

```bash
cd phase1_uart   # or phase5_apb
python mutation_suite.py        # full report + sim_build/mutation_report.json
```

`mutation_suite.py` is a thin manifest (mutant list + mechanisms) built
on the generic, DUT-agnostic engine in `mutation/` -- the same engine,
unmodified, drives both DUTs. The report shows total/caught/survived,
combined score, a per-mechanism breakdown, a per-defect-category
breakdown, and a per-mutant table (which mechanism(s) caught it). UART
additionally has two older, narrower, single-mechanism scripts preserved
unchanged from Phase 3, `run_mutants.py` and `run_mutants_checker.py`.

## Formal verification (APB only)

Three properties on `apb_regblock`, proven with a free, pip-installable
toolchain (`yowasp-yosys` + `yowasp-yosys-smtbmc` + `z3-solver`, driven
by SymbiYosys, auto-fetched on first use -- no sudo, no commercial EDA
license, no billing):

```bash
python run_regression.py --skip-mutation --skip-lint   # formal runs by default
```

| Property | Result |
|---|---|
| P1: PSLVERR correctness | PASS -- bounded (BMC, depth 5); complete for this specific claim since the property is purely combinational (see `VERIFICATION_STRATEGY.md` for why that distinction matters) |
| P2: no restart while busy | **PASS -- unbounded (k-induction)** |
| P3: BUSY bounded by `OP_LATENCY` | **PASS -- unbounded (k-induction)** |

Full details -- exact assumptions, toolchain limitations verified (not
assumed), and two real modeling issues found and fixed during
implementation -- are in `phase5_apb/VERIFICATION_PLAN.md` and
`VERIFICATION_STRATEGY.md`. **These properties are not SVA**: every one
is a plain procedural `assert`/`assume` statement, verified to parse and
execute on this toolchain; SystemVerilog `property`/`sequence` blocks
were never tested and are not claimed to work here.

## Waveform debugging

cocotb's Icarus Verilog Makefile flow supports waveform dumping out of
the box via `WAVES=1` -- no Makefile changes required:

```bash
cd phase1_uart      # or phase5_apb
make clean
make WAVES=1
gtkwave sim_build/uart_tx.fst    # or sim_build/apb_regblock.fst
```

This dumps an FST file (GTKWave's native format) covering the full DUT
hierarchy. In GTKWave, drag signals from the SST panel into the signal
list to view them. To convert to VCD (for tools that don't read FST),
use `fst2vcd` (ships with GTKWave):

```bash
fst2vcd sim_build/uart_tx.fst -o sim_build/uart_tx.vcd
```

A failing formal property produces its own real counterexample `.vcd`
directly (see "Formal verification" above and "Failure diagnostics"
under "Quick start") -- no `WAVES=1` needed for that case.

## Lint

```bash
cd phase1_uart && verible-verilog-lint uart_tx.v
cd phase5_apb && verible-verilog-lint apb_regblock.v
```

[Verible](https://github.com/chipsalliance/verible) checks style and
structural issues. Findings are reported, not auto-fixed, where fixing
them would conflict with another constraint (documented per-DUT in each
`VERIFICATION_PLAN.md` -- mainly that most of the remaining findings
would require regenerating every mutation-suite mutant to preserve the
"exactly one injected difference from golden" property those files
depend on).

## CI

`.github/workflows/regression.yml` runs the same `run_regression.py` on
every push/PR to `main`, on GitHub's free `ubuntu-latest` runners --
GitHub Actions is free for public repos and has a generous free tier
otherwise, with no billing anywhere in this workflow. It installs Icarus
Verilog via `apt-get` and every Python dependency (including
`verible-verilog-lint` and the formal-verification toolchain) from
`requirements-lock.txt`, fetches SymbiYosys, then runs the regression and
uploads the report and any failure artifacts.

**Status of remote CI verification:** the exact commands this workflow
runs (`pip install -r requirements-lock.txt`, `python run_regression.py`,
etc.) have been verified locally, including from a byte-fresh virtual
environment using only `requirements-lock.txt`. The workflow YAML has
been validated for syntax and structure. This repository is not
currently connected to a GitHub remote with an executed Actions run, so
a real remote CI execution has not been observed -- that verification is
pending, not claimed.

## `phase2_llm/`: LLM-assisted verification (separate track)

A comparison, not part of the regression/CI/mutation-engine work above:
the same UART TX RTL and mutants, verified instead by a testbench
generated by an LLM (Gemini) from a natural-language prompt, scored with
the same mutation-testing methodology for comparison against the
hand-written UART testbench. See `phase2_llm/` directly; it is
deliberately untouched by every phase after its introduction.
